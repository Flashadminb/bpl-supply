## วิธี deploy

ห้าม `wrangler pages deploy` — โปรเจกต์นี้เป็น Worker ไม่ใช่ Pages

```bash
npx.cmd vite build
npx.cmd wrangler versions upload          # ได้ URL ทดสอบ ไม่แตะของหน้างาน
npx.cmd wrangler versions deploy <id>@100% --yes   # ปล่อยขึ้นจริง
npx.cmd wrangler deployments status       # ดูว่าหน้างานใช้เวอร์ชันไหน
```

**ค่าเริ่มต้นคือ upload ก่อนเสมอ** ส่ง URL ทดสอบให้เจ้าของระบบดู
แล้วค่อย deploy เมื่อเขาสั่ง ย้อนกลับได้ด้วย `versions deploy` ตัวเก่า

ต้องใช้ `npx.cmd` ไม่ใช่ `npx` — PowerShell เครื่องนี้บล็อก `.ps1`

## วิธีรัน migration

ไฟล์อยู่ใน `supabase/migrations/` และมีสำเนาที่ `supabase/update-0XX.sql`
ทุกไฟล์ต่อท้ายลงใน `supabase/setup-all.sql` ด้วย

รันโดยเปิดหน้า Supabase SQL Editor ในเบราว์เซอร์แล้ววางลงไป
Claude ทำให้ได้ถ้ามีส่วนขยาย Chrome

**ตรวจ dollar-quoting ก่อนรันเสมอ** จำนวน `$` ต้องเป็นเลขคู่ทุกชนิด tag
เคยพลาดเพราะนับผิดมาแล้ว

### กฎการเขียน migration ที่ต้องถือ

ฐานข้อมูลมีชุดเดียว migration ลงแล้วมีผลกับหน้างาน **ทันที**
ต่อให้ยังไม่ปล่อยหน้าเว็บก็ตาม

- **เพิ่มของใหม่** (ตาราง คอลัมน์ที่มีค่าตั้งต้น ฟังก์ชันชื่อใหม่) = ปลอดภัย
- **แก้ทับของเดิม** (ฟังก์ชันที่แอพเรียกอยู่ RLS คอลัมน์) = กระทบทุกคนเดี๋ยวนั้น

ถ้าต้องแก้ฟังก์ชันที่ใช้งานอยู่ ให้คัดลอกตัวจริงมาแล้วเติมเฉพาะส่วนใหม่
แล้ว `diff` เทียบให้เห็นว่าเป็นการ **เพิ่มอย่างเดียว** ไม่มีบรรทัดไหนถูกแก้หรือลบ

## งานวันที่ 12 ต.ค. 2569 · สิ่งที่ตัดสินใจไว้

### พัสดุค้างเกิน 24 ชม · หน้าใหม่ไอคอนเลข 24
ชื่อมาจากเนื้อหาในไฟล์ ไม่ใช่ชื่อไฟล์ · ของชิ้นที่ค้างน้อยสุดในไฟล์แรกคือ 25.2 ชม
แปลว่าต้นทางกรองมาให้แล้วว่าเกินกรอบ 24 ชม
หน้าแรกเป็นผังกิ่ง แกนกลางคือการดำเนินการล่าสุด เริ่มที่ยกเลิกการส่งต่อพัสดุเสมอ
โซน D0 ใช้ `hub_out_zones` ร่วมกับของค้างส่งออก ตั้งที่เดียวใช้สองหน้า

### อัปไฟล์ทับได้ และไม่เก็บย้อนหลัง
เจ้าของระบบสั่งว่าของพวกนี้ไว้ให้หน้างานดูสถานะ ไม่ต้องเซพ
ทั้งสองกระดานเก็บแค่ 3 รอบล่าสุด เปลี่ยนที่ `board_keep_rounds()` ที่เดียว
ที่ไม่เหลือรอบเดียวเพราะลูกศรเทียบรอบก่อนต้องมีรอบที่แล้วเป็นตัวเทียบ

### ประวัติการแก้ไขบัตรเบรค
บันทึกด้วย trigger ที่ตัวตาราง `break_passes` ไม่ใช่ให้แต่ละ RPC เขียน log เอง
ถ้าให้แต่ละตัวเขียนเอง วันหนึ่งจะมีทางแก้ข้อมูลทางใหม่ที่คนเขียนลืมใส่
แล้วประวัติจะมีรูโดยไม่มีใครรู้ว่ามีรู
เหตุผลที่คนพิมพ์ส่งผ่าน `set_config('app.break_reason', ...)` ของ transaction นั้น

### OT ต่อเวลาคืนเครื่อง
`due_at` ไม่ถูกเลื่อนตามเด็ดขาด · ที่เพิ่มคือ `ot_until`
ถ้าเลื่อนกำหนดเดิมทิ้ง สิ้นเดือนจะไม่มีใครรู้ว่าใบนี้เลยเวลามาตั้งแต่กี่โมง
และสถิติทั้งเดือนจะสวยเกินจริงโดยไม่มีใครตั้งใจโกง
ต่อได้ 1 2 3 4 ชม เฉพาะคนที่เบิกเอง และครั้งเดียวต่อใบ
กติกา "ตอนนี้เลยเวลาหรือยัง" อยู่ที่ `isLate()` ใน `src/lib/assetOt.ts` ที่เดียว

### บุ๊กมาร์กเมนูหลังบ้าน
เก็บใน localStorage รายคน ไม่ได้เก็บลงฐานข้อมูล
เพราะเป็นความชอบส่วนตัวที่เปลี่ยนบ่อยและไม่มีใครอื่นต้องรู้
ข้อแลกคือเปลี่ยนเครื่องแล้วต้องติดดาวใหม่

### ป็อปอัพแจ้งเตือนของแอพ
อยู่บนหน้าแรกเท่านั้นโดยตั้งใจ หน้าสแกนและกล้องจึงไม่มีทางโดนบัง
จำว่าใครเห็นอะไรที่ฐานข้อมูล ไม่ใช่ในเครื่อง เก็บ 14 วันแล้วลบตอนอ่าน
แจ้งเตือนรับเฉพาะเรื่องของแอพ · กระดานปล่อยรถ รถรอลงงาน ของค้างส่งออก
พัสดุ 24 ชม ไปเตือนในกระดานของมันเอง

### กล่องที่ชี้แล้วขึ้นบนหน้าแรกหลังบ้าน
ห้ามเว้นช่องว่างระหว่างตัวการ์ดกับกล่อง และห้ามใส่ `pointer-events-none`
ไม่งั้นเมาส์เดินไปไม่ถึงกล่อง มันดับก่อน และเลื่อนในกล่องไม่ได้
วิธีที่ใช้คือให้กล่องชิดขอบการ์ด แล้วดันระยะห่างเข้าไปเป็น padding ข้างใน

## งานวันที่ 13 ต.ค. 2569 · สิ่งที่ตัดสินใจไว้

### กดเครื่องในตารางหน้าแรกแล้วสั่งงานได้เลย
ตารางบนหน้าแรกเรียกกล่อง `AssetDeviceBox` ตัวเดียวกับหน้ากระดาน ไม่ได้ทำกล่องใหม่
ถ้าทำใหม่ วันหนึ่งกติกาฝั่งหนึ่งจะเปลี่ยนแล้วอีกฝั่งไม่เปลี่ยนตาม
แล้วจะมีเครื่องที่โอนจากหน้าแรกได้แต่โอนจากกระดานไม่ได้ โดยไม่มีใครรู้ว่าทำไม
โหลดแบบ `lazy` เพราะข้างในลากกล่องถ่ายรูปและกล่องโอนติดมาทั้งชุด
ของกองนี้ไม่ควรไปอยู่ในก้อนของหน้าแรกซึ่งทุกคนต้องโหลดก่อนเสมอ
กระดาน `asset_board` ถูกขอตอนกดเครื่องแรกเท่านั้น ไม่ได้ขอตั้งแต่เปิดหน้า
กด "ดูทั้งหมด" ไปหน้ากระดาน ไม่ใช่หน้า Asset ที่ยังไม่คืน
เพราะกระดานคือที่เดียวที่กรอง ค้นหา และสั่งงานได้ครบในหน้าเดียว

### ป้ายเบรคเกินเวลาบนหน้าแรก · ทำไมมีสามตัวเลข
วัดของจริงวันที่ 12 ต.ค. — ปิดใบ 492 ใบใน 24 ชม
เกินเกิน 1 นาที 232 ใบ · เกิน 5 นาที 51 ใบ · เกิน 15 นาที 3 ใบ · เกิน 30 นาที 1 ใบ
แปลว่า "เกิน 1 นาที" คือเวลาเดินกลับเข้าประตู ไม่ใช่การอู้
นาฬิกาเริ่มเดินตอนหัวหน้ายื่นบัตร เวลาเดินไปประตูจึงอยู่ในนั้นด้วย
ถ้าขึ้นหน้าแรกว่าวันนี้เกินเวลา 232 ใบ จะไม่มีใครอ่านป้ายนี้อีกเลยตั้งแต่วันแรก
ป้ายจึงเรียงจากเกินนานสุดและตัดที่ 15 ใบ แล้วเขียนทั้งสามเลขให้เห็นว่าภาพจริงเป็นยังไง

### ป้ายเบรคอยู่ได้ 24 ชม แต่ใบที่ยังไม่กลับไม่มีกำหนดหาย
ใบที่กลับเข้ามาแล้วแต่เคยเกิน อยู่ต่อ 24 ชม นับจากเวลารับกลับ แล้วหายเอง
ใบที่ยังไม่กลับไม่นับอยู่ในกติกานั้น เพราะมันไม่ใช่ประวัติ มันคือคนที่ยังไม่กลับเข้ามา
ใบที่หลังบ้านปิดเองไม่นับว่าเกินเลย ใช้กติกาเดียวกับ `over_sec` ใน view `break_rows` เป๊ะ ๆ
เวลาที่ค้างมาจากการลืมกดรับกลับ ไม่ใช่คนนั้นอยู่ข้างนอกจริง

### พัสดุ 24 ชม · หน้างานดูได้แล้ว
เปิดเฉพาะ "ดู" · อัปไฟล์กับถอนรอบยังเป็นของผู้ดูแลระบบ
อัปทับคือลบของเดิมทั้งกระดาน ถ้าใครก็กดได้ วันหนึ่งจะมีคนกดพลาด
แล้วทั้งฮับจะมองกระดานเปล่าโดยไม่รู้ว่าเกิดอะไรขึ้น

กันสองชั้น · ฐานข้อมูลเป็นด่านจริง (`parcel24_import` ยังเป็น `my_can_outbox()`)
ส่วนหน้าจอแค่ไม่เอาปุ่มที่กดไม่ได้ไปวางให้คนกด
ปุ่มสลับหน้า จอทีวี/หน้าหลัก/ตาราง ย้ายออกมาเป็นแถบของตัวเอง
เพราะของเดิมมันอยู่ในแถบอัปไฟล์ ซ่อนแถบนั้นแล้วหน้างานจะสลับหน้าไม่ได้

ทางเข้าของหน้างานใช้ลิงก์งาน (`work_links`) แบบเดียวกับกระดานอื่น ๆ
เปิดให้ดูแล้วแต่ไม่มีทางเข้า ก็เท่ากับไม่ได้เปิด

## สองเครื่องแยกกัน · บทเรียน 12 ต.ค. 2569

เครื่องที่บ้านกับเครื่องที่ทำงานหลุดจากกันหนึ่งคอมมิต แล้วเกือบทับงานกันทิ้ง

สิ่งที่เกิดจริง
- เครื่องที่ทำงานมีคอมมิต `c6517c1` "จัดหน้าแรกใหม่" ที่**ไม่เคยถูก push**
- เครื่องที่บ้าน clone มาจาก GitHub จึงไม่มีคอมมิตนั้น ทำงานต่อแล้ว push ขึ้นไปสองคอมมิต
- พอ deploy จากบ้าน เว็บจริงจึงเป็นเวอร์ชันที่**ไม่มีไทล์ปล่อยรถกับรถรอลงงานบนหน้าแรก**
  ซึ่งเจ้าของระบบเห็นแล้วนึกว่าเวอร์ชันถอยหลัง

ทางที่ถูกตอนเจอสถานการณ์นี้ ห้ามข้ามขั้น
1. `git fetch` แล้วดู `git rev-list --left-right --count HEAD...origin/main`
2. ดูว่าสองฝั่งแตะไฟล์ชนกันไหม `git diff --stat HEAD...origin/main`
3. **commit ของในเครื่องให้หมดก่อน** แล้วค่อย `git merge origin/main`
   ห้าม `pull` ทับตอนยังมีของค้าง และห้าม `reset --hard` เด็ดขาด
4. build ให้ผ่าน แล้วตรวจว่าของทั้งสองฝั่งยังอยู่ครบจริง ไม่ใช่เชื่อว่า merge แล้วต้องครบ

**และเรื่องไอคอนหาย ส่วนใหญ่ไม่ใช่โค้ดหาย แต่เป็น service worker เสิร์ฟของเก่า**
ตรวจของจริงด้วยการ curl bundle จากเว็บมา grep ไม่ใช่เชื่อสิ่งที่เห็นบนจอเครื่องตัวเอง

```bash
LIVE=$(curl -s https://bpl-supply.elevenezbest.workers.dev/ | grep -o 'assets/index-[A-Za-z0-9_-]*\.js' | head -1)
curl -s "https://bpl-supply.elevenezbest.workers.dev/$LIVE" | grep -c "ตารางปล่อยรถ"
```

## บัตร OS นำโทรศัพท์เข้าพื้นที่

รปภ สแกน QR ที่บัตรคล้องคอ ระบบโชว์รูปหน้ากับข้อมูลเครื่องให้เทียบกับคนตรงหน้า

| ใคร | ทำอะไรได้ |
|---|---|
| รปภ (`can_guard`) | สแกนอย่างเดียว · หน้าแรกเป็นคนละหน้า ไม่มีเมนูเบิกของ |
| ผู้ตรวจสอบขึ้นไป | จัดการรายชื่อ ออกบัตร ยกเลิก ดูประวัติ พิมพ์บัตร |

**รปภ อ่านตาราง `os_people` ตรง ๆ ไม่ได้** ต้องผ่าน `os_scan()` ซึ่งเป็น security definer
และตอบเฉพาะคนที่บัตรใบนั้นชี้ถึง — ไม่ให้ดึงรายชื่อทั้งฮับพร้อมรูปและ IMEI ออกไปได้

**QR มีแค่โค้ดสุ่ม 16 ตัว** ไม่มีชื่อ ไม่มี IMEI ถ่ายรูปบัตรคนอื่นไปก็ไม่ได้ข้อมูลใคร

ความยาวโค้ดไม่ใช่เรื่องความปลอดภัยอย่างเดียว แต่ตัดสินว่าสแกนติดไหมด้วย
ของเดิม 32 ตัวคละพิมพ์เล็กใหญ่ QR ต้องใช้ตาราง 29×29 เหลือช่องละ 0.47 มม.
16 ตัวพิมพ์ใหญ่ล้วนเข้ารหัสแบบตัวอักษรได้ เหลือ 21×21 ช่องโตขึ้นเกือบเท่าตัว
ความสุ่ม 80 บิตยังเดาไม่ได้ และการเดาต้องยิงผ่าน `os_scan` ซึ่งบันทึกทุกครั้ง
**ห้ามต่อข้อมูลอื่นเข้าไปใน QR** เช่นชื่อหรือ URL จะดันกลับไป 29×29 ทันที
ออกบัตรใหม่ = ยกเลิกใบเก่าในคำสั่งเดียวกัน ไม่งั้นการออกบัตรใหม่ตอนบัตรหายจะไม่มีความหมาย

**ตั้งใจไม่มีการเตือน "สแกนซ้ำ"** OS เดินออกห้องน้ำวันละหลายรอบ
ถ้าเด้งทุกรอบ รปภ จะกดผ่านโดยไม่อ่านภายในวันเดียว แล้วคำเตือนจะไร้ค่าในวันที่สำคัญจริง

**กดแจ้งไม่ตรง** ต้องเลือกเหตุผลเสมอ ยิงหาผู้ตรวจสอบ + คนที่แผนกย่อยเป็น `STD`
(เปลี่ยนรหัสทีมที่ `app_settings.os_flag_sub_dept` ไม่ต้อง deploy)

พ่วงไปกับการส่งยอดเบิกประจำวันจะดึงของที่ไม่มีใครขอดูทุกครั้ง ต้องขอ scope `osscan`

**ปุ่มส่งเฉพาะช่วงวันที่ที่เลือกอยู่บนจอ** ไม่ได้ส่งทั้งหมด
ซึ่งมีกับดักว่าของค้างนอกช่วงจะไม่มีวันถูกส่งโดยไม่มีอะไรบอก
จึงนับของค้างทั้งหมดมาเทียบแล้วขึ้นป้ายเหลืองว่าต้องขยายช่วงก่อน
เป็นกับดักเดียวกับที่เคยเจอในหน้าส่งยอดเบิก

**ชีตนี้คือที่เก็บระยะยาว** เพราะ `os_scans_rollup` ยุบรายละเอียดรายครั้งทิ้ง
หลังผ่านไปอย่างน้อย 30 วัน เหลือแค่สรุปรายวัน
ของที่ไม่ได้ส่งลงชีตก่อนถึงรอบยุบจะหายไปเลย

## สิทธิ์เข้าถึง — เฉพาะเจ้าของระบบ

`/admin/access` · `adminOnly` · แอดมินทั่วไปเข้าไม่ได้
คนที่ยกสิทธิ์ให้คนอื่นได้ ต้องยกสิทธิ์ให้ตัวเองได้ด้วย ซึ่งไม่ควรเป็นของทุกแอดมิน

**สิทธิ์รายคน** รวมสวิตช์ทุกตัวไว้ที่เดียว เปิดปิดอิสระต่อกัน
`can_assets` · `can_proxy` · `can_sack` · `can_dispatch` · `can_guard`
เพิ่มธงใหม่ให้ไปต่อในอาร์เรย์ `FLAGS` ที่หัวไฟล์ แถวในตารางสร้างจากอาร์เรย์นั้น
เปลี่ยน**ตำแหน่ง**ยังทำที่หน้าผู้ใช้และสิทธิ์เหมือนเดิม ที่นี่ไม่แตะตำแหน่ง
แผนกที่เห็นเพิ่ม (`extra_depts`) ก็ยังอยู่ที่หน้าเดิม ไม่ย้ายมาซ้ำสองที่

**`can_proxy` คุมทั้งเบิกแทนและโอนเครื่อง** เพราะฐานข้อมูลใช้ `my_can_proxy()`
ตัวเดียวกันทั้งใน `create_requisition`, `asset_checkout` และ `asset_transfer_many`
ป้ายบนหน้าจอจึงเขียนว่า "เบิกแทน/โอนเครื่อง" ตามความจริง
**ถ้าจะแยกสองอย่างนี้ ต้องเพิ่มธงใหม่และแก้ `asset_transfer_many` ด้วย**

**`canProxy()` เคยถูกยืมไปใช้อีกสามที่** (ของทั้งฮับ วางแผนประชุม ประชุมค้าง)
ที่ความหมายจริงคือแอดมินหรือผู้ตรวจสอบ ตอนนั้นเงื่อนไขบังเอิญเหมือนกัน
ตอนนี้แยก `canAudit()` ออกมาแล้ว **อย่าเอา `canProxy` กลับไปใช้แทนอีก**
ไม่งั้นหน้างานที่ได้สิทธิ์เบิกแทนจะเห็นของทั้งฮับตามไปด้วย

### เครื่องเฉพาะคน

`asset_user_grants` · เปิดให้คนหนึ่งคนเห็นเครื่องหนึ่งเครื่องนอกเหนือจากแผนกตัวเอง

**คนละเรื่องกับการโอน** การโอนย้ายเครื่องไปอยู่กับคนนั้นจริงและเป็นของชั่วคราว
อันนี้แค่มองเห็นและเบิกได้ เครื่องยังเป็นของแผนกเดิม ค้างจนกว่าจะเอาออก

ข้อใหม่ใน policy `read_assets` อยู่ในวงเล็บของ `my_can_assets()` เหมือนข้ออื่น
คนที่ถูกปิดสิทธิ์ Asset ไว้จึงไม่ได้สิทธิ์ย้อนกลับมาเพราะถูกให้เครื่องรายตัว

**เจ้าตัวต้องอ่าน `asset_user_grants` ได้** policy ของ `assets` อ้างตารางนี้
ถ้าปิดไม่ให้เจ้าตัวอ่าน จะมองไม่เห็นแถวของตัวเองแล้วสิทธิ์จะไม่ทำงาน
เขียนได้เฉพาะผ่าน RPC และเฉพาะเจ้าของระบบ

`asset_checkout` เป็น security definer จึงไม่เช็กแผนกซ้ำ อาศัย `read_assets` อย่างเดียว
**ให้สิทธิ์เห็น = เบิกได้ด้วย** ซึ่งตั้งใจ

## สถานะโอน-แจ้งเสีย — หน้ารวมประวัติ

เมนูต่อจาก "สถานะเบิก-คืน" · `/admin/asset-moves` · **ผู้ตรวจสอบเห็นด้วย**
เป็นหน้าอ่านอย่างเดียว ไม่ได้เปลี่ยนสถานะที่โชว์ที่อื่นเลยสักจุด

สองแท็บ: ประวัติการโอนทั้งฮับ (ใครโอนอะไรไปให้ใคร ใครกดโอน ปลายทางรับหรือยัง)
กับใบแจ้งเสียทั้งฮับ พร้อมตัวกรอง "เฉพาะที่ยังไม่ได้เคลียร์"

อ่านจากวิว `asset_transfer_rows` กับ `asset_issue_rows` ซึ่งเป็น `security_invoker`
จึงยึด policy เดิมที่เปิดให้แอดมินกับผู้ตรวจสอบอยู่แล้ว ไม่ได้เปิดกว้างขึ้น

**คนละตัวกับ `asset_transfer_notices`** ตัวนั้นคือ "ของค้างอยู่ของฉัน" ของหน้างาน
ตัวใหม่เห็นทั้งหมดรวมของที่จบไปแล้ว เพราะเป็นหน้าไว้ดูย้อนหลัง

ช่วงวันที่ตั้งต้นย้อนหลัง 30 วัน ไม่ใช่วันเดียวเหมือนหน้าอื่น
การโอนกับของพังไม่ได้เกิดทุกวันเหมือนการเบิก ตั้งวันเดียวแล้วหน้าจะว่างเกือบตลอด
ซึ่งคนเปิดมาจะคิดว่าระบบไม่ทำงาน

### แจ้งเสียจากหน้าทะเบียน

`asset_report_issue()` · ปุ่มอยู่ในแผ่นรายละเอียดเครื่อง เหนือหัวข้ออาการค้าง
เผื่อหน้างานไม่แจ้งแล้วแอดมินเดินไปเจอเอง

ของเดิมอาการพังบันทึกได้ตอนเบิกหรือตอนคืนเท่านั้น เครื่องที่วางอยู่เฉย ๆ
จึงต้องรอให้มีคนมาเบิกก่อนถึงจะแจ้งได้ แปลว่าของพังถูกเบิกออกไปหนึ่งรอบเสมอ

`phase` ปล่อยว่าง เพราะไม่ได้เกิดตอนเบิกหรือคืน หน้าจอแปลว่า "แจ้งจากทะเบียน"
ของเดิมอ่าน `phase` แบบเผื่อ null อยู่แล้ว ข้อมูลที่ย้ายมาจากชีตก็ไม่มี phase
อาการเดิมที่ยังไม่เคลียร์และข้อความเหมือนกันเป๊ะถือว่ากดซ้ำ ไม่บันทึกใหม่

## กระสอบ — ใครเห็นงานนี้

ธงรายคน `profiles.can_sack` กดเปิดปิดได้ที่คอลัมน์ **กระสอบ** ในหน้าผู้ใช้และสิทธิ์
ของเดิมหน้างานทุกคนเห็น ยกเว้นผู้ตรวจสอบ ซึ่งเลือกไม่ได้ว่าใครควรเห็น

ผู้ตรวจสอบเปิดไม่ได้ ขึ้นขีดแทน ตามที่เจ้าของระบบสั่งว่าเอากระสอบออกจากผู้ตรวจสอบทั้งหมด
แอดมินกับเจ้าของระบบเห็นเสมอโดยไม่ต้องเปิดธง เพราะเห็นอยู่แล้วโดยหน้าที่

**บังคับที่ฐานข้อมูล ไม่ใช่แค่ซ่อนปุ่ม** `my_can_sack()` คุม policy อ่านทั้ง `sack_orders`
และ `sack_order_photos` · `mark_sack_sent` เช็คซ้ำในตัวเอง เพราะเป็น security definer
จึงข้าม policy ไปได้ · เส้นทาง `/ship` ก็กันด้วย ไม่ใช่ซ่อนแค่ไทล์บนหน้าแรก

ตอนเพิ่มธงนี้ backfill ให้คนที่เคยแตะงานกระสอบจริงกับแอดมิน ที่เหลือปิด
**ธงใหม่ที่เพิ่มทีหลังให้ทำแบบนี้ด้วย** เปิดค้างไว้ให้คนที่ใช้งานอยู่ ไม่งั้นตัดเขากลางกะ

## กระสอบ — จำนวนที่ส่งจริง

สาขาขอ 500 ของในฮับมีไม่พอ ส่งได้ 200 · ช่อง `sent_qty` เก็บจำนวนที่ส่งไปจริง
ว่างแปลว่าส่งเต็มตามที่ขอ **ไม่ได้แปลว่าไม่รู้** แถวเก่าก่อนมีช่องนี้จึงยังอ่านถูก

**ในใบขึ้นแต่จำนวนที่ส่ง ไม่ขึ้นว่าขอเท่าไหร่** เจ้าของระบบกำชับไว้
ใบนี้ไปอยู่ในแชทกลุ่มที่มีสาขาปลายทางอยู่ด้วย ตัวเลขที่ขอแล้วไม่ได้ของ
ทำให้ต้องไปนั่งอธิบายกันในกลุ่ม · ส่วนต่างโผล่ในหน้าประวัติฝั่งเว็บที่เดียว

**หน่วยก็เลือกตอนส่งได้** (`sent_unit`) สาขาขอมาเป็นชิ้น แต่หน้างานนับตอนขึ้นรถเป็นกระสอบ
ของเดิมหน่วยล็อกตั้งแต่ตอนตั้งรายการ ต้องแปลงหัวคิดเอง ซึ่งแปลว่ามีวันที่แปลงผิด

**`qty_differs` จริงเฉพาะตอนหน่วยเดียวกัน** ขอ 700 ชิ้น ส่ง 20 กระสอบ
ไม่ได้แปลว่าขาด 680 แต่แปลว่าคนละหน่วย หน้าประวัติขึ้นป้าย "คนละหน่วย" แทนการคำนวณส่วนต่าง
ตัวกันพิมพ์ตกหลัก (สิบเท่า) ก็เทียบเฉพาะตอนหน่วยเดียวกัน ไม่งั้นจะบล็อกการส่งที่ถูกต้อง

`mark_sack_sent` เปลี่ยนจากสี่ช่องเป็นหก ช่องที่เพิ่มมามีค่าเริ่มต้น
แอปรุ่นเก่าที่ยังเรียกแบบสี่ช่องจึงยังทำงานได้ ซึ่งจำเป็น
เพราะ service worker ทำให้บางเครื่องใช้โค้ดเก่าต่ออีกหลายชั่วโมงหลัง deploy
**เปลี่ยนลายเซ็นฟังก์ชันคราวหน้าให้ทำแบบนี้ด้วย**

ยังไม่มีคอลัมน์นี้ในชีตกระสอบ เจ้าของระบบขอแค่ในเว็บ

## ส่งออก Google Sheet — เพดานพันแถวของ PostgREST

**อาการ** กดส่งแล้วขึ้นสำเร็จทุกครั้ง แต่ตัวเลข "ยังไม่ส่ง" ไม่ลด
รายงานว่า "เพิ่มใหม่ 0 แถว · อัปเดตของเดิม 1036 แถว" ซ้ำ ๆ

**สาเหตุ** PostgREST ส่งกลับมาสูงสุด 1000 แถวต่อครั้ง (`db-max-rows`)
และไม่ได้บอกว่าตัด — ตอบ 200 มาเฉย ๆ เหมือนดึงครบแล้ว
พอ Asset เกินพันบรรทัด ตัวส่งออกจะวนส่งพันบรรทัดแรกซ้ำทุกครั้ง
บรรทัดใหม่ไม่เคยถูกดึงมาเลย ทุกอย่างดูปกติทั้งสองฝั่ง

**แก้แล้วใน `paged-v11`**
- `dbPaged()` ไล่ทีละหน้าจนหมดจริง (416 = หมดแล้ว ไม่ใช่พัง)
- ทุก query ต้องมี `order` ที่ไม่ซ้ำกัน ไม่งั้นแถวสลับหน้ากันแล้วหายหรือซ้ำ
  เติม `,id.asc` ต่อท้ายทุกอันที่เรียงด้วยเวลาอย่างเดียว
- `lookupPlaced()` แบ่งคีย์เป็นก้อนละ 200 แทนที่จะยัดลง `in.(...)` ทีเดียว
  ของเดิมพังสองทาง URL ยาวเกิน และผลลัพธ์โดนตัดที่พันแถวอีกชั้น

**ถ้าเจออาการนี้อีกที่อื่น** มองหา `db<X[]>(...)` ที่ไม่มี limit
ทุกจุดที่ดึงรายการจาก PostgREST มีเพดานเดียวกันหมด

**อีกกับดักในหน้าเดียวกัน** ปุ่มส่งทำงานกับ *ช่วงวันที่ที่เลือก* เท่านั้น
แต่เลขบนเมนูข้างนับย้อนหลังสองปี ของที่ค้างนอกช่วงจึงไม่มีวันถูกส่ง
ตอนนี้ขึ้นป้ายเหลืองบอกว่ามีกี่บรรทัดค้างอยู่นอกช่วง และต้องขยายช่วงก่อน

## เบิกแทนคนอื่น

ทำได้ทั้งสองฝั่งแล้ว ใช้ด่านเดียวกันคือ `my_can_proxy()`
เจ้าของระบบ · แอดมิน · ผู้ตรวจสอบ

| ฝั่ง | ฟังก์ชัน | คอลัมน์คนกด |
|---|---|---|
| Asset | `asset_checkout(..., p_for_user)` | `asset_txns.acted_by` |
| สิ้นเปลือง | `create_requisition(..., p_for_user)` | `requisitions.acted_by` |

`requester_id` ยังหมายถึง "คนที่ของไปอยู่ด้วย" เหมือนเดิมทั้งสองฝั่ง
ของค้างคืน ประวัติ และแจ้งเตือน จึงไปหาเจ้าตัวโดยไม่ต้องแก้อะไรเลย

**ตัวเลือก "เบิกให้ใคร" ไม่เก็บลงเครื่อง** ต่างจากตะกร้าที่ค้างข้ามวันได้
ถ้าจำไว้ข้ามกะ วันรุ่งขึ้นแอดมินจะเบิกของตัวเองเข้าชื่อคนอื่นโดยไม่รู้ตัว
ปิดแอพแล้วเปิดใหม่จึงกลับไปเป็น "เบิกเอง" เสมอ

ป้ายเตือนขึ้นสามที่: หน้าตะกร้า · หน้าถ่ายรูป (กดแก้กลับได้ตรงนั้น) · หน้าเบิกสำเร็จ
ลายน้ำบนรูปประทับชื่อ **คนรับ** ไม่ใช่คนถือกล้อง เพราะรูปคือหลักฐานว่าของไปอยู่กับใคร

**ยังไม่ได้ทำ** คอลัมน์ "คนกดเบิกให้" ในไฟล์ส่งออก Google Sheet
ของฝั่งเบิก-คืนยังมีเท่าเดิม ถ้าจะเพิ่มต้องต่อท้าย `HEADER` ใน `export-sheet`

### การ์ดรูป — กว้าง 1080 เสมอ สูงตามเนื้อหา เพดาน 1920

ความสูงเดินตามฝั่งที่ยาวกว่าระหว่างบล็อกข้อมูลกับกองรูป
**เพดาน 1920 ห้ามถอด** ยาวกว่าจอมือถือแล้วต้องเลื่อนดู
ซึ่งเสียจุดประสงค์ของการ์ดใบเดียวจบ ของเดิมเคยยาวตามจำนวนรูป
หกใบได้ภาพสูงเกือบหกพันพิกเซล เปิดในแชทเห็นเป็นแถบผอม ๆ

ตรึงไว้ที่ 1920 เสมอก็ไม่ได้เหมือนกัน รูปนอนสองใบกินแค่ราวพันสองร้อย
เหลือพื้นดำอีกเจ็ดร้อยใต้ของที่ต้องดู วัดจากเคสตัวอย่าง
สองรูป 1217 · สามรูป 1689 · รูปเดียว 996

**รูปเริ่มที่ระดับเดียวกับบรรทัดแรกของข้อมูล** ไม่ได้จัดกลางคอลัมน์
สองฝั่งจึงเสมอกัน ซึ่งเป็นสิ่งที่เจ้าของระบบขอ

รูปทั้งหมดอยู่ในใบเดียว (`grid`) เพราะงานจริงส่วนมากมีสองรูป
ยังมี `split` (รูปละใบ) อยู่ในโค้ด เผื่อวันที่ต้องแนบเยอะจนช่องเล็กเกินอ่าน
เปลี่ยนที่ค่าตั้งต้นของ `buildSackCards()` บรรทัดเดียว

**ข้อมูลอยู่คอลัมน์ซ้าย รูปได้ฝั่งขวาทั้งแถบ**
ของเดิมข้อมูลกินเต็มความกว้างด้านบน รูปได้แถบล่างที่เหลือ
รูปจึงสูงได้ไม่เกินราวครึ่งการ์ด ทั้งที่รูปคือของที่คนเปิดมาดูจริง
ส่วนข้อความอ่านสองรอบก็จำได้แล้วว่าช่องไหนคืออะไร

**ช่องของแต่ละรูปเท่ากัน** (`SackPhotoFit` ค่าตั้งต้น `equal`) เจ้าของระบบขอให้ดูบาลานซ์
เคสปกติไม่ต่างจากแบ่งตามสัดส่วนเลย เพราะคนเดิมถ่ายด้วยเครื่องเดิมถือแนวเดียวกัน
สัดส่วนจึงเท่ากันทุกใบอยู่แล้ว ต่างกันแค่ตอนมีรูปตั้งปนรูปนอนในใบเดียว

**ความสูงช่องยึดรูปที่เตี้ยที่สุด ไม่ใช่สูงที่สุด** เอาตัวสูงสุดเป็นเกณฑ์แล้ว
รูปนอนจะลอยอยู่กลางช่องสูง ๆ ช่องเท่ากันก็จริงแต่รูปข้างในสูงไม่เท่า ตายังเห็นว่าไม่เท่า
แถมดันการ์ดยาวออกไปด้วยแถบดำที่ไม่มีอะไรอยู่
เอาตัวเตี้ยสุดแล้วทุกใบสูงเท่ากันจริงและไม่มีแถบดำบนล่าง
แลกกับรูปตั้งที่เล็กลง ซึ่งเกิดเฉพาะตอนมีตั้งปนนอน

**ช่องเท่ากันไม่ได้แปลว่ารูปจะดูเท่ากันเป๊ะ** รูปตั้งกับรูปนอนสูงเท่ากันได้
แต่กว้างไม่เท่ากัน ตราบใดที่ยังไม่ครอบขอบ
มีตัวเลือก `equalCrop` ที่ครอบขอบให้เต็มช่องจนเท่ากันเป๊ะ แต่ไม่ได้ตั้งเป็นค่าตั้งต้น
เพราะป้ายบนกระสอบมักติดอยู่ริม ๆ รูป ครอบแล้วมีโอกาสตัดสิ่งที่ต้องดูทิ้ง

ย่อรูปให้พอดีกรอบ ไม่ครอบขอบทิ้ง เพราะป้ายมักติดอยู่ริม ๆ ของ

**เลขที่อยู่ท้ายการ์ดตัวเล็ก ไม่ได้อยู่หัวการ์ด** หน้างานดูจำนวนกับสาขา
เลขที่ใช้ตอนแอดมินตามเรื่องย้อนหลัง หัวการ์ดจึงเก็บไว้ให้ของที่ต้องเห็นก่อน

ใบที่ไม่มีรูปกว้าง 752 ไม่ใช่ 1080 คงไว้เท่าใบที่มีรูปจะเหลือพื้นดำเปล่าเกือบครึ่งใบ
ซึ่งดูเหมือนรูปโหลดไม่ขึ้น มากกว่าดูเหมือนใบที่ตั้งใจไม่มีรูป

**จะแก้หน้าตาการ์ด ให้ดูของจริงก่อน** `node sack-preview.cjs` แล้วเปิด
`/__sack-preview.html` (หรือ `/__sack-fit.html` เทียบวิธีแบ่งช่องรูป) — สองหน้านี้ import ตัวจริงจาก `sackCard.ts` ผ่าน Vite
มีเคสรูปนอน ตั้ง จัตุรัส และข้อมูลยาว ซึ่งเป็นเคสที่ทำเลย์เอาต์พัง ไม่ใช่เนื้อในรูป

ใบที่มีรูปออกเป็น JPEG 0.92 (2 รูป ≈ 116KB) ใบที่ไม่มีรูปเป็น PNG และไม่ยืดเต็มจอ
ถ้าอยากให้ชัดกว่านี้อีกต้องขึ้น `MAX_EDGE` (ตอนนี้ 1024) ซึ่งแลกมาด้วย egress

### แก้ไขรายการ

พิมพ์จำนวนผิดไม่ต้องลบแล้วตั้งใหม่ · ปุ่ม **แก้ไข** ในตาราง (เจ้าของระบบกับแอดมิน)
ผ่าน `update_sack_order()` · แก้ได้ทั้งใบที่ยังไม่ส่งและใบที่ส่งไปแล้ว

ที่ต้องยอมให้แก้ใบที่ส่งแล้วด้วย เพราะเคสที่เจอบ่อยคือตั้งไว้ผิด
หน้างานส่งของตามจำนวนจริง แล้วค่อยมารู้ทีหลังว่าเลขในระบบผิด
ถ้าล็อกไว้ ตัวเลขจะผิดถาวรโดยไม่มีทางแก้
หน้าจอเตือนไว้ว่าใบที่ส่งไปแล้วจะไม่ตรงกับฟอร์มเดิมที่เขาส่งออกไป

ช่องไหนไม่ส่งมา = ไม่แตะช่องนั้น · หมายเหตุส่งสตริงว่าง = ลบทิ้ง
ทุกครั้งที่แก้บันทึก `updated_at` / `updated_by` และขึ้นในตารางว่าใครแก้
`needs_push` ของชีตนับการแก้ไขด้วย ไม่งั้นชีตจะค้างเป็นตัวเลขเก่าตลอดไป

แก้ไม่ได้: สถานะการส่ง สาขาที่ฝาก และรูป — สามอย่างนั้นเป็นของหน้างาน
ไม่ใช่ของคนตั้งรายการ ถ้าแก้ได้จากฝั่งนี้ก็ไม่ต่างกับกรอกแทนเขา
